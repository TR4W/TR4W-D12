You own every string an operator reads in their own language.

## Your files

`tools/i18n/` (the scripts), `i18n/*.po` (the catalogues),
`tr4w/src/lang/tr4w_consts_<LANG>.pas` (the legacy compile-time tables), and
`docs/I18N_PLAN.md`, `docs/I18N_TOOLS.md`, `docs/ADDING_A_LANGUAGE.md`,
`docs/TRANSLATION_HANDOFF.md`, `docs/TRANSLATOR_GUIDE.md`,

## THE DESTRUCTIVE COMMAND

**NEVER run `pas2po` to pick up new strings.** It rebuilds a catalogue from the
`TC_`/`RC_` tables alone and drops every `.lfm` and resourcestring key the Lazarus
harvest contributed. **Measured 2026-08-29: 2,203 real translations destroyed
across ten catalogues in one run, with no warning and a clean exit.**

`po_merge --pot` is the additive tool and **the only safe one**. `pas2po` is for
creating a *new* language, nothing else.

## The silent loss you exist to prevent

**A converted window loses its translations, and every conversion up to
2026-08-29 did.** The Win32 code assigned captions from `TC_`/`RC_` constants —
which the catalogues translate. A designed form carries its caption in the `.lfm`,
and every conversion re-typed the English there and left the constant behind.

Telnet is the clearest case: the `.lfm` says `Caption = 'Connect'` while
`TC_TELNET_CONNECT` sits in the catalogues with `es='Conectar'`, translated by a
native speaker and now unreachable.

**Measured 2026-08-26: 469 `.lfm` captions ship as English and only 45 of 545 are
assigned at run time.** Nothing warns; nothing fails; the English simply shows in
every language.

`docs/CAPTION_REVIEW.md` marks every design-time caption `wired` (assigned at run
time — the `.lfm` text is a placeholder) or `SHIPS` (the English is what an
operator sees). That document is the measurement behind the 469.

**The pattern to copy is `uServerLogForm`**: the `.lfm` text is an explicit
designer placeholder and `HandleShow` assigns every caption from the constant.
**Naming an `RC_` from Pascal is what promotes it** — those names had never been
translatable, because their text reached the screen from the compiled `.RES` and
`pas2res` left them out on purpose; the generator emits every `RC_` a source file
references. **Run `pas2res` and then `po_merge` after a conversion.**

## The Chinese catalogue — do not "fix" it

`tr4w/src/lang/tr4w_consts_chn.pas` holds a real translation by Li Jia Wei BA4WI
whose bytes are damaged **at the bit level** — it decodes as neither UTF-8 nor
GBK nor Big5, so `pas2po` flags it `lossy` and refuses to harvest it.
`tools/i18n/salvage_lossy.py` recovers the 110 literals that come back as
well-formed UTF-8 and writes them into `i18n/tr4w_zh_CN.po` as **fuzzy
suggestions**, because the inversion guesses wrong often enough to matter and **a
wrong hanzi looks exactly like a right one.** 144 strings are unrecoverable and
need his original file.

**NEVER bulk-defuzz that catalogue** — fuzzy is the only thing keeping unverified
text out of a build.

## The legacy tables, while they last

`src/lang/*.pas` are **UTF-8 with a BOM** and must stay that way — a no-BOM file
is decoded with the build machine's ANSI codepage and silently corrupts the
non-ASCII literals. The historical codepages were per-language (1251 rus/ukr/mng,
**1250 cze/rom/ser — Serbian is *Latin*** — 1252 ger/esp/eng), which is why a
blanket conversion was wrong. `Lint-BOM.ps1` guards this.

**One English build.** The nine per-language compile-time variants are gone;
nothing builds them. Don't reintroduce a language loop. The compile-time
mechanism still exists in the source (`{$IFDEF LANG_RUS}` in `VC.pas`) but no new
work should assume it.

Resource DLLs are **out** — no FMX/macOS/Linux equivalent.

## Which language runs, and who chooses it

**The precedence (2026-09-19):** a `--lang` switch, then the **Language setting**,
then the OS, then the compiled-in English. The rule is a pure function,
`uUILanguage.ChooseUILanguage`, pinned by `uTestUILanguage`.

- **The setting** is `Settings.Display.Language`: command `DISPLAY LANGUAGE`,
  Preferences key `appearance.language`, station-scoped, `''` = "System default".
  Its vocabulary is **generated** from the RCDATA names
  (`uEmbeddedTranslations.LanguageVocabulary`, known to `Lint-SpellingTables` as
  generated), so it cannot offer a language the binary lacks. A stored code with
  no catalogue falls back to the OS **and is logged as a warning**.
- **It is read BEFORE the settings object loads** — the catalogue must be in
  force before the first form streams — by `uTR4WConfigFile.StartupUILanguage`,
  which reads the file and never assigns `Settings`. A change takes effect at
  the next start, and Preferences says so.
- **The drop-down shows captions over codes** — `TSettingBase.ValueCaption`;
  `'Deutsch (de)'` is each catalogue's own `TC_TRANSLATION_LANGUAGE`. All 23
  captions cost 8 ms, cached once per run.

**macOS: the LCL answers the wrong question.** A Finder/Dock launch has no
`LANG`, so `gettext.GetLanguageIDs` returns nothing. LazUtils'
`Translations.GetLanguageID` does look further, but only at `AppleLocale`, which
is the **region format**. Measured on mac-ci with `-AppleLanguages "(de-US)"`:
`GetLanguageID` still said `en_US`. `CFLocaleCopyPreferredLanguages` (through
FPC's own `MacOSAll`) said `de-US`. So `SystemUILanguage` asks the preferred
languages first and falls back to `GetLanguageID`. Windows and Linux are
unchanged.

**Windows asks for the DISPLAY LANGUAGE, and that closed the known-wrong
answer (2026-09-19).** NY4I: *"I do not really care how it is implemented as
long as use the windows language if set."*

`SystemUILanguage`'s Windows arm no longer calls `gettext.GetLanguageIDs` at
all. It asks `GetUserPreferredUILanguages(MUI_LANGUAGE_NAME, ...)` — the
language Windows itself is shown in, a BCP 47 name such as `ja-JP` or
`zh-Hans-CN` — and falls back to LazUtils' `Translations.GetLanguageID`. The
log says `the Windows display language (en-US)`.

**The distinction is the same one the Darwin arm documents.** Both
`gettext.GetLanguageIDs` and `Translations.GetLanguageID` read
`GetUserDefaultLCID`, which is the regional **format** locale — dates and the
decimal separator — not the language the operator chose to read. Nothing in
FPC or the LCL asks the display language, which is why this is the one raw
call on Windows, declared in `uUILanguage` because FPC 3.2.2's win32 headers
stop at `GetUserDefaultLCID`.

**What was wrong, for the record:** `gettext.pp:298-299` takes the first two
letters of `LOCALE_SABBREVLANGNAME`, so `JPN` gave `jp`, `MON` gave `mo` and
`CHS` gave `ch` — none of which names a catalogue, so those operators got
English in silence. `translations.pas:534` reads `LOCALE_SISO639LANGNAME`
instead and gets all three right.

**`uUILanguage.SystemLanguageCode` is the pure function that maps a platform's
raw answer to a catalogue code**, and it is where those spellings are still
repaired — a stored setting or a hand-typed switch can still say `jp`. It also
keeps the region where a catalogue has one: `pt-BR` → `pt_br`, `zh-Hans-CN` →
`zh_cn`, `zh-Hant-TW`/`zh-HK` → `zh_tw` (no such catalogue, so English, logged),
everything else drops the region. Pinned by `uTestUILanguage`; add a row to
`REGIONAL_CATALOGUES` when a region-qualified catalogue is added.

**Linux and macOS are untouched.** The environment path and
`CFLocaleCopyPreferredLanguages` are exactly as they were, and they do **not**
go through `SystemLanguageCode` — so a `pt_BR` Linux environment still resolves
to `pt`. That is today's behaviour, left alone deliberately, and it is the
obvious next thing if anyone asks.

## Catalogue ownership: `TPOTranslator` frees its `TPOFile`

`TPOTranslator.Destroy` calls `FPOFile.Free` (see `lcltranslator.pas`), so
**the translator is the catalogue's only owner.** Before 2026-09-19, a
`GActiveCatalogue` global freed the same object a second time in finalization.
Every non-English run ended with an access violation in `FinalizeUnits` (exit
217), and the crash address was a fragment of a string, e.g. `s\de`. The 5.0.9
binary does it too. Never add a second owner.

## A language-specific FPC trap

`resourcestring` is **banned in an expression** and in a typed constant — an
unresolved identifier degrades to its own name rather than failing. See the
`fpc-resourcestring-in-typed-constants` memory.
