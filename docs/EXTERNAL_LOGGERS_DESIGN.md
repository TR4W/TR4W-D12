# External logger definitions, factory and delivery

Implemented in worktree `codex/external-loggers-191`, based on `aedfe202afe1f873aa800df58f1a6ba76235e8c2`. Design approved by NY4I on November 4, 2026. Issue [191](https://github.com/TR4W/TR4W-D12/issues/191) is the Club Log pilot. All implemented providers handle new contacts, changes and deletes, except Cloudlog/Wavelog (issue 204) and ACLog (issue 33), whose programs have no edit or delete call: there an edit or delete of a delivered contact fails visibly.

## Configuration and operator setup

Open Preferences > External Software > External Logger. **The grid is the editor** (issue 220; there is no separate list dialog). It lists configured loggers in active delivery order, then inactive definitions, with Order (the delivery position; a dash means the logger is not active, so Order and Send new QSOs are one fact), Logger, Provider, **Enabled** (a checkbox: the same flag as Order and the popup's Send new QSOs, one fact in `ActiveIds`) and **Connection** (issue 226). Enabled and Order apply on Save, live (issue 233, below); until Save the row reads "Applies on Save", and "Restart TR4W to apply" is kept for what only a restart changes (a logger added since start, or changed connection settings). Connection is the running program's answer: `DeriveExternalLoggerState` over a `TExternalLoggerSnapshot` (`TExternalLoggerService.StateSnapshot`, filled from the delivery worker's locked status and, for DXKeeper, its queue depth) plus the durable counts, refreshed every 5 s while the page shows. States: Disabled, Restart TR4W to apply, Idle, Sending (n pending), Retrying: code, Paused: code (halted worker: auth, URL refused, setup required), Failed: code (last delivery refused, or the worker died). Old failed or uncertain rows only add counts to the text. Text carries the meaning; colour repeats it.

- **Add...** opens the one-definition editor with a provider choice; OK appends the definition (inactive until the operator ticks Active or switches Send new QSOs on).
- **Right-click a row** (or double-click it): Edit..., Send new QSOs (checked item; double-clicking that cell also toggles it), Move up, Move down, Remove. Switching Send new QSOs ON runs the same checks as the editor's OK (required fields, unique names, the shared-destination question) and is refused if they fail.
- **Drag the Order cell** to reorder (`goRowMoving`; the LCL starts a row drag only from a fixed column, which is why Order is the fixed column). Move up/down use the grid's own `MoveColRow`, so they take the drag's path. Either way the new order is written back: `Definitions` follow the grid, and `ActiveIds` becomes the active rows in grid order, which is the delivery order. A row dropped across the active/inactive line snaps back to its group.
- **Remove** asks for confirmation and drops the definition from both lists. It leaves the vault and any queued deliveries alone (below).

Save Preferences to apply Enabled and Order now; a new logger, or changed connection settings, applies after a restart (issue 233, below). Multiple instances of a provider are allowed. A running service keeps the settings it was started with, so an in-flight operation cannot be redirected by an edit in the grid.

The grid edits the Preferences working copy directly, so Cancel (which reloads it) discards every grid edit; the outer Save or Save and close persists them. The per-definition editor uses a private copy; its Save to Preferences returns that one definition to the working copy, and its Cancel discards the dialog's edits without touching the vault. Preferences Save uses the existing single JSON writer. An empty active list deliberately disables delivery. Deactivation pauses durable delivery and stops acquiring new contacts, but subsequent edits/deletes to existing bindings are still captured for later delivery. Removing a definition explicitly leaves its queued rows in the contest log; they are not redirected to another definition. Keep a settings backup if the definition might need to be restored.

Passwords and API keys live in the existing platform keychain under definition IDs. JSON contains references, never newly written plaintext credentials. Names/order are not credential identity. During migration, an unreadable legacy WRL key keeps a reference to its original vault name until the new reference can be stored.

Club Log uses a personal token created under Settings > API. Only the token and destination callsign are needed; no account email, password or developer application key is sent. The callsign must belong to the token's account. The earlier pilot selected the obsolete multipart API; this was corrected on November 5 after NY4I supplied the working REST request and the current issue comment.

DXKeeper, WRL, Club Log, Cloudlog and ACLog register constructor functions from their implementation units. Adding Club Log required no provider branch in the QSO logging path or dispatcher. Future providers register their constructor and editor-field metadata (and, optionally, a default port that a new definition of that provider starts with) through the same registry. The HRD placeholder is not registered as a working provider. `lt_ACLog` and `lt_WRL` remain in `ExternalLoggerType` only as the legacy single-logger setting's TOKENS (the settings vocabulary and the migration); nothing delivers through them.

## Queue and thread invariants

The main thread snapshots live QSO/contest/station state. Existing DXKeeper formatting still runs there because it reads live state. The dispatcher receives immutable command values with destination IDs and only enqueues them to sender workers. Durable providers additionally capture local intent inside the QSO transaction and wake their independent workers after commit. This small local database write is intentional: a committed QSO must not depend on an in-memory notification surviving a crash.

No DNS, TCP, HTTP, retry wait or worker join runs on the logging path. Disabled definitions do not create idle sender workers. A blocked HTTP request holds no database transaction and does not hold up another destination's worker. The existing UDP and HamScore paths remain separate dispatcher sinks.

Order means enqueue/start priority and per-contact revision ordering, not completion order across networks. TCP command queues are FIFO; durable outboxes coalesce contact revisions and schedule by retry deadlines. Waiting for destination one to finish before destination two would make an unavailable service block the rest.

**Live apply (issue 233, 2026-11-06).** uProgramMain calls StartExternalLoggerFromSettings once at startup and builds one service per saved definition (an inactive one owns no worker); closing/reopening a contest calls LogClosed without reconstructing services. Saving Preferences now calls `ApplyExternalLoggerConfiguration` after the file is written, which runs `TExternalLoggers.ApplyConfiguration` on the main thread and then `LogStoreStartExternalDelivery`. The rule, in one place:

- **The set of services is fixed for the session; only their switches and the delivery order change.** The dispatcher thread reads `FServices`/`FIds` and nothing else of the composite, so it never sees a list change. The switches, the order and the command count are main-thread state, read when a message is PREPARED. A message prepared before Save is delivered to the destinations it was prepared for (once); one prepared after follows the new switches. Nothing is lost or delivered twice. Pinned with the dispatcher held open mid-delivery while Save applies.
- **Off always applies.** It stops NEW handoffs. A durable service asks its worker to stop and parks it (never joined on the main thread; the delivery in flight settles first); its outbox is untouched. DXKeeper's in-memory queue keeps draining. Edits and deletes of contacts already bound to a logger are still captured, as before. A definition REMOVED in Preferences is switched off.
- **On applies only to a service whose settings are what it was started with.** `TExternalLoggerDefinition.SettingsStamp` hashes the provider and every field it reads, secrets included, and the definition's certificate choice `VerifyServer` (issue 256) (not Name, LogbookName, and not `DeliveryId`, which names the durable queue; the choice is in the stamp and NOT in `DestinationFingerprint`, so ticking the box never parks the backlog). A definition added since start, or whose stamp differs, keeps running as started (or stays off) until restart, and its row reads "Restart TR4W to apply"; Preferences' status line counts them after Save. Putting the edit back clears it. This also means a key edited while the logger is on keeps the OLD key sending until restart, which is the point: queued work is never retargeted.
- **Enabling starts that destination for NEW contacts from that moment.** Contacts logged while it was off were never captured and are not backfilled (the existing no-implicit-backfill rule). Work already queued resumes at once. Disable then re-enable quickly never runs two workers: the retiring worker stays parked until it has exited, and the watchdog tick starts the replacement only if the service is still enabled.
- **Order** is the saved active list, applied by delivery id.

Not live: adding a service. That needs the composite's list to change under a running dispatcher thread and is left for a later change (a service can already exist for a definition added in an earlier session).

The set of services is immutable during a session. Producers/dispatcher must be stopped before closing its services. Shutdown requests all workers to stop before waiting, with one shared one-second deadline. An unfinished service is detached and retained until process exit rather than freeing resources still used by its worker. Durable work remains on disk. The existing DXKeeper in-memory queue does not gain crash persistence in this change; undelivered commands retain its explicit diagnostics.

Each durable instance's namespace contains its stable ID plus a SHA-256 fingerprint of destination settings. Display-name/order and credentials do not participate. Changing a server/account/logbook parks the old namespace, so an old backlog cannot be sent to the new destination. Claims, recovery, capture bindings and gap markers are scoped by that namespace. No schema-version change is needed: the existing logger key already holds strings.

WRL's migrated definition adopts only legacy rows matching its original account and logbook, including confirmed rows and remote IDs. Other accounts/logbooks are not adopted. Adoption is per contest file and does not resend a confirmed contact. Legacy commands/settings are migration input; after the new section exists, the definition library is authoritative and the old singleton does not override it.

## Cloudlog and Wavelog (issue 204, 2026-11-07)

One provider, `CLOUDLOG`, for both programs (`uCloudlogClient`, `uCloudlogExternalLogger`). They share one API: `POST <address>/api/qso`, JSON `{"key", "station_profile_id", "type":"adif", "string"}`. The key is in the BODY, not an Authorization header. An instance served through `index.php` enters its address as `https://host/index.php`. The facts below were read from the two programs' source (Api.php and Logbook_model.php on GitHub); no live server has been run, so the bench queue holds the live checks.

**Answers and what TR4W does with each:**

| Answer | Meaning | Outcome |
| --- | --- | --- |
| 201 `created`, Cloudlog `imported_count` 1, or Wavelog `adif_count` 1 and `adif_errors` 0 | the one record sent was taken | confirmed (local marker `cloudlog:created` as the remote id, because neither server returns one) |
| 201 with `imported_count` 0 (Cloudlog duplicate), `adif_count` 0, or `adif_errors` above 0 | refused: a 201 does not prove an import | failed `CLOUDLOG_IMPORT_REJECTED`, destination keeps running |
| 400 `abort` (Wavelog) | the import refused this contact (a duplicate, a validation error) | failed `CLOUDLOG_IMPORT_REJECTED`, keeps running |
| 401 | bad key, a profile the key's owner does not own, or (Cloudlog) a STATION_CALLSIGN not matching the profile, or an empty call | the worker's rule: work kept, destination paused |
| 403 | read-only key (Wavelog) | the same |
| 200 `status:failed` | malformed JSON | failed `CLOUDLOG_REQUEST_REFUSED`, paused |
| 429 | rate limit (Wavelog) | retry after Retry-After, 60 s if absent |
| other 4xx, 3xx | wrong address or similar; redirects are not followed | failed `CLOUDLOG_HTTP_n` / `CLOUDLOG_REDIRECT`, paused |
| 5xx, no or unreadable answer, a count that fits nothing | the import may have happened | uncertain, paused, never replayed blindly |
| nothing sent (TLS or CA bundle unavailable, plain http, no scheme) | proved by `NothingSent` | the shared `ApplyNothingSent` table, `CLOUDLOG_*` codes |

**EDIT AND DELETE: NOT SUPPORTED, AND THIS IS A DECISION FOR NY4I.** Neither server has an edit or delete endpoint, and a re-POST is not a substitute: both match call, minute, band, mode and station and refuse a match as a duplicate (Wavelog 400, Cloudlog `imported_count` 0), and an edit that changes one of those fields would add a SECOND row. So an edit or delete of a contact already delivered settles as a visible failure (`CLOUDLOG_EDIT_UNSUPPORTED`, `CLOUDLOG_DELETE_UNSUPPORTED`): nothing is sent, nothing is reported as synced, the row shows Failed with the code, and the destination keeps sending later contacts (the failures do not pause it). A contact never delivered is unaffected: an edit of one whose create was refused is simply sent, and a delete of one is cancelled locally. This departs from the rule above that every implemented provider handles changes and deletes. The alternatives are to send the edit as a new contact (risks a duplicate in the remote log) or to leave edits and deletes out of that destination's queue silently (the rule forbids it). The operator corrects the remote log by hand in Cloudlog or Wavelog.

**TLS and the key.** Certificates are checked when the global setting AND the definition's own "Verify the server's certificate" box (issue 256, `HTTP_TRANSPORT_DESIGN.md` section 13) are both on, so a self-signed LAN site is reached by clearing that one definition's box (the editor shows a warning while it is cleared, and the log names the destination). The address must be `https://`; a plain-http LAN site is still refused with a visible code (question 12 in `HTTP_TRANSPORT_DESIGN.md`, which waits for NY4I). The key is sent as the request's Password with no Username, so `uHTTPDownload` masks it in every log line (the `[HTTP]` body line reads `"key" : "********"`) while no Authorization header is made. A key containing characters that JSON escapes (a slash, a quote) would not match its raw form in the logged body; Cloudlog and Wavelog keys are alphanumeric, and this is unverified for anything else.

## ACLog (issue 33, 2026-11-08)

Provider `ACLOG` (`uACLogClient`, `uACLogExternalLogger`), a durable provider of the Cloudlog shape. AC Log is the TCP SERVER: the operator enables "TCP API Enabled" in AC Log; the default port is 1100. Facts are from `docs/N3FJP Application Program Interface (API).md`; no live AC Log has been run (BENCH_QUEUE holds the live checks).

**Wire.** Each command is one line, `<CMD>...</CMD>` ended by CR LF; a bare CR LF ends the connection. TR4W sends, per contact, on its own connection (worker thread, never shared): `<CMD><ADDADIFRECORD><VALUE>` + the ADIF record (the same `ADIFContactForExternal` text Club Log and Cloudlog get) + `</VALUE></CMD>` + CR LF, then a bare CR LF, then closes. UTF-8. The record's own trailing CR LF is dropped and any other CR or LF inside it becomes a space (same length), because a CR LF anywhere would end the command early. `<`, `>` and `&` in the record are sent as they are (the API's own example does). Pinned byte for byte in `uTestACLog` against a loopback server.

**Decisions (made before the build):**

| Situation | Outcome |
| --- | --- |
| Connect refused, timed out, host unresolvable (nothing written): AC Log not running or its API off | `doRetry`, 60 s, NOT paused, `ACLOG_NOT_REACHABLE`. The queue waits and drains when AC Log is back. |
| Command fully written | `doConfirmed`, local marker `aclog:added` as the remote id (the outbox refuses a confirmed create with none). **This is a TCP hand-off, not an acknowledgement**, the same standing as DXKeeper's. No reply is read. |
| Failure after the connection was up, part-way through the write | `doUncertain`, paused, `ACLOG_SEND_REQUIRES_REVIEW` (the record may be partly there; never replayed blindly). |
| Edit of a contact already handed over | `doFailed`, not paused, status 0, nothing sent, `ACLOG_EDIT_UNSUPPORTED`. |
| Delete of a contact already handed over | the same, `ACLOG_DELETE_UNSUPPORTED`. |
| Delete of a contact never delivered | settled confirmed locally, nothing sent. An edit of one never delivered is a create. |
| Empty host, or port outside 1..65535 | paused, `ACLOG_SETUP_REQUIRED`, nothing sent. |

The shared `ApplyNothingSent` table is HTTP-only (it reads a `THttpRequest`) and does not apply to a raw TCP client.

**Why no edit or delete.** The API documents no call to change or remove a logged record and returns no record id. This breaks the rule that every implemented provider handles changes and deletes, as Cloudlog does, and is the same departure: an unsupported operation fails visibly and the operator corrects AC Log by hand.

**Settings.** Host (`LF_ADDRESS`, required) and port (`LF_PORT`), the same two rows DXKeeper declares and the same captions. A provider can register a default port (`RegisterExternalLogger`'s last argument): ACLog 1100, DXKeeper 52001. Choosing a provider in the editor moves a port still at the old provider's default (or empty) to the new one's; a port the operator typed stays. The durable owner needs a destination name and a non-empty credential slot, so the destination is `host:port` and the credential is a fixed placeholder that is never sent. Host and port are in `DestinationFingerprint`, so changing either parks the old backlog.

**Migration.** A legacy `EXTERNAL LOGGER = ACLOG` is seeded as an `ACLOG` definition with the legacy host. The legacy port setting defaults to 52001 (DXKeeper's), so a legacy port still at that value is replaced by the provider's own default (1100); a port the operator chose is kept. `lt_ACLog` stays in the legacy token vocabulary (`ExternalLoggerTypeSA`) so an old settings file still loads.

**Scope.** `ADDADIFRECORD` writes straight to the log: callbook lookup, contest scoring and the dupe sheet are bypassed. This provider targets AC Log, not the N3FJP contest programs, where a bypassed score would be wrong.

**Unverified.** No reply to `ADDADIFRECORD` is documented (the n3fjp-mcp spec has none either), so success cannot be known; whether AC Log accepts raw `<`, `>`, `&` and non-ASCII (UTF-8) inside `<VALUE>`; how it treats a duplicate; the ADIF band spelling and mode it reads. No live AC Log has been run.

## Changes, deletes and uncertainty

A worker claims a revision, commits the claim, sends it, then settles that revision. A newer local revision remains pending after the older request completes. A delete before an unsent create is cancelled locally. An edit/delete arriving while a create is in flight is subsequently applied using the confirmed remote version.

Club Log stores the numeric qsoid returned by POST /api/v1/qso. Replacements first DELETE /api/v1/qso/{qsoid}, then POST the new ADIF with its destination call. Deletes carry no body or edited identity fields. A failed delete never proceeds to create; a 404 requires review rather than assuming the ID belonged to this account. An undelete after a confirmed deletion creates a fresh contact. If replacement creation fails after the delete, the operation pauses as uncertain: the old QSO has gone, so replaying the two-step replacement blindly is unsafe.

The outbox preserves both current and confirmed payloads. If a reply is lost, the outcome is uncertain; it is not silently marked successful. Club Log also treats interrupted replacement requests as uncertain on restart because a replacement contains a create and may already have installed a different remote identity. WRL retains its existing recovery policy for operations keyed by a remote ID.

Authentication errors stop the affected worker. Club Log pauses on other failed/unrecognised responses as well, avoiding automatic request storms. The editor shows pending/in-flight/synced/uncertain/failed durable counts. Fix credentials/configuration and restart for a paused worker; uncertain remote state requires reconciliation before replay. No bulk real-time backfill or whole-log deletion is introduced.

## Protocol evidence and live acceptance

The current [real-time upload documentation](https://clublog.org/support/knowledgebase/rest-api/uploads-and-adif/how-to-upload-qsos-in-real-time/), [delete documentation](https://clublog.org/support/knowledgebase/rest-api/uploads-and-adif/how-to-delete-qsos-in-real-time/) and [REST contract summary](https://clublog.org/support/knowledgebase/rest-api/for-llms/club-log-api-information-for-llms/) supersede the old multipart examples. The interactive OpenAPI reference requires a logged-in browser session; the public articles explicitly document the implemented requests.

POST /api/v1/qso accepts JSON containing call plus one adif record. A real creation returns HTTP 201, status created and a numeric qsoid. HTTP 200 duplicate/updated is accepted only with a valid qsoid, so future changes/deletes never invent an identifier. Missing IDs and unrecognised or dropped responses require review. DELETE /api/v1/qso/{qsoid} returns HTTP 200 status deleted. All requests carry Authorization: Bearer and User-Agent: TR4W, with HTTPS and redirects disabled.

An accepted test-mode creation (HTTP 201, status created, test_mode true, qsoid null) counts as successful delivery and advances the outbox to synced, per NY4I's November 5 testing requirement. The local marker clublog:test-mode satisfies the outbox's nonempty delivery-identity invariant; it is never sent as a qsoid. Edits validate another upload; deletes settle locally because no remote QSO exists. A later edit with a normal token creates a real contact and replaces the marker with the returned numeric qsoid. Rejected/malformed replies remain failures even if they contain test_mode true. Use a designated test token while validating requests. HTTP 429 respects Retry-After; authentication, access, validation and unknown-ID errors stop the destination. Transport/5xx write outcomes require reconciliation rather than blind replay. Account quotas are shared with other clients; no whole-log backfill is added. Live persisted create/change/delete acceptance remains necessary with an explicitly designated logbook and normal token.

## Validation

After the REST correction, full application and unit-test builds pass, as do all 54 repository lints and the staged whitespace check. The latest worktree suite, including the accepted test-mode lifecycle, reports 423,944 checks passed and zero failures. Local capture/commit while HTTP was blocked measured 0 ms. Application warning gates remain at their existing ceilings (3 range warnings and 1,201 narrowing conversions). A curl smoke request using NY4I's supplied test token and the same call/adif JSON shape returned status created, qsoid null, test_mode true and nothing stored; no real QSO was created. Coverage includes definition/vault JSON round trips; active ordering and idempotent migration; class-factory construction of WRL and Club Log; per-destination preparation/enqueue containment; native form streaming; Club Log create/change/delete/undelete and failed-delete suppression; destination-isolated capture/claims/recovery; inactive binding updates; legacy row adoption; and simultaneous real worker threads with one HTTP operation deliberately blocked.

The blocked-worker fixture measures the local capture/commit while that HTTP operation is in flight and checks that the other destination drains. These are local fixture measurements, not a claim about every radio, platform or remote service. Existing WRL capture benchmarks remain in the suite.

## Handoff: observed startup delivery failure

On November 5, NY4I observed a startup warning before logging a new contact. Read-only inspection of the worktree test contest showed the existing W7EDT 15m CW delivery (2026-11-05 06:09:58 UTC), revision 2, with no remote ID. Startup resumes pending work; it does not manufacture a new QSO. The application log at 01:19:44 local recorded TLS unavailable before HTTP, followed by CLUBLOG_RESPONSE_REQUIRES_REVIEW with HTTP 0. TLS loading remains to be investigated, and the client should distinguish a proven pre-request setup failure from an ambiguous write outcome. No user delivery rows were cleared or rewritten. The existing uncertain row will not be automatically replayed by changing the test-mode success policy.

Resolution (NY4I rulings, November 5): `THttpRequest.TlsUnavailable` marks the proven pre-request failure (https asked for, `EnsureOpenSSL` false, no byte sent). Club Log and WRL classify it as `doRetry` with `CLUBLOG_TLS_UNAVAILABLE` / `WRL_TLS_UNAVAILABLE` and a 300 s delay, never uncertain; the diagnostic text is in tr4w.log, written once per distinct text. On Windows `EnsureOpenSSL` retries a failed load after 30 s. The HTTP layer now logs method, URL, exception class and message for every failed request, credentialed or not; the bearer token and form password are scrubbed out of all of it (`uHTTPDownload.MaskSecret` / `ScrubSecret`, raw and URL-encoded) and each request writes one DEBUG line, tagged `[HTTP]`, with the whole request WE SEND (method, URL, headers, body) and every secret masked as a fixed `********`; nothing received (response body or headers) is logged at any level (issue 229). Pinned in `uTestHttpSecrets`. A missing or unreadable CA bundle (`ApplyTLSVerification` refusal, issue 221) is classified the same way: `THttpRequest.TrustBundleMissing`, `doRetry`, 300 s, `CLUBLOG_CA_BUNDLE_MISSING` / `WRL_CA_BUNDLE_MISSING`. `cacert.pem` is looked for in the data directory, then beside the program; the operator gets one notice per service per session (the worker's `Notice`, shown by the owner on the main thread). HamScore (not a delivery worker) keeps its QSOs on the same refusal: `PostToServer` returns 0, the cycle retains them, its status line reads "Not sent: cacert.pem not found (looked in: ...)" and `TrustBundleAlertText('HamScore')` writes the once-per-session log line. The contest score post and the interactive downloads (CTY, TRMASTER, POTA, version check) are one-shot operator actions: they show the refusal's `FailReason`, which names the places looked, and change no stored state. An OS trust-store fallback is not part of this: FPC never calls `SetDefaultVerifyPaths`, and reaching the Windows store (crypt32) or macOS Keychain needs a new library binding, which waits for the platform transports of issue 224 (S2+).

Accepted test-mode responses now settle successfully with a local-only marker; rejected responses and transport failures do not. The rebuilt worktree executable is build-out/app-i386-win32/tr4w_external_loggers.exe, named separately to leave the running test application untouched.
