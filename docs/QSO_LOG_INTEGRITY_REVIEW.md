# TR4W QSO log integrity review

Reviewed November 21, 2026 against `main` at `6924737c`. The scope is the station log, from submitting a contact to reopening the SQLite database or restoring a backup. The multi-op server is covered where its behavior affects that guarantee.

## Assessment

**The ordinary single-row logging path has a sound local commit boundary.** TR4W commits each row before adding it to the log grid or clearing the operator's entry. On local storage with effective `WAL` and `synchronous=FULL`, SQLite synchronizes the WAL on every commit. A committed row may still live in the WAL, so keep the WAL with the database during recovery and use TR4W’s Backup Log for a standalone copy while logging. The highest-priority application defects are publication before commit, partial saves of a single multi-row exchange, and edits or deletes that can appear successful after a failed write. The clearest latency risk is a full backup on the same thread that handles Enter. [Enter path](../tr4w/src/MainUnit.pas#L1228) · [Local append](../tr4w/src/uLogStore.pas#L2894) · [SQLite synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous) · [SQLite WAL file](https://www.sqlite.org/wal.html#the_wal_file)

## How a contact reaches disk

1. `TryLogContact` validates the exchange and calls `LogContact`. `LogContact` stamps the contest rules and network identity. `tAddQSOToLog` asks `uLogStore` to append the row. The repository inserts the row with the sent exchange, station facts and any grouping identifier. Configured durable external loggers can capture pending delivery in the same transaction. Their worker starts after commit, and a worker-start failure leaves the committed QSO in place. [Entry](../tr4w/src/MainUnit.pas#L1228) · [Contact preparation](../tr4w/src/trdos/logsubs2.pas#L1677) · [Repository insert and commit](../tr4w/src/uLogStore.pas#L2949) · [Durable delivery capture](../tr4w/src/uDurableExternalLogger.pas#L101)
2. The successful commit advances the grid and record count. Scoring, display refresh, periodic backup and optional restart-state work also run before the manual entry handler finishes. For a refused single-row save, the handler preserves the call and exchange. The WSJT-X caller also stops its success path after a refusal. A write that hits disk full or a classified write I/O error can leave a readable log open after rollback. The next local save can probe for recovery and proceed after space is freed. A log opened read-only due to a startup lock stays that way for the session. [Grid acknowledgement](../tr4w/src/trdos/logsubs2.pas#L2835) · [After commit](../tr4w/src/trdos/logsubs2.pas#L1920) · [Write recovery](../tr4w/src/uLogStore.pas#L1434) · [WSJT-X](../tr4w/src/uWSJTX.pas#L1458)
3. The store checks database and foreign-key integrity on open and performs a write probe on writable opens. It takes a verified snapshot before upgrading an older SQLite schema. Schema changes and the version stamp commit together. Clear Log also requires a verified backup before deleting rows. Live snapshots use a separate connection, include committed WAL rows, and pass integrity and foreign-key checks before publication. Periodic backup is disabled by default. When enabled, the local snapshot and verification run inline, with an optional copy to another destination. [Schema and migration](LOG_SCHEMA.md#1-file-identity-pragmas-and-compatibility) · [Open checks](../tr4w/src/uLogStore.pas#L2249) · [Clear Log](../tr4w/src/MainUnit.pas#L10193) · [Verified backup](../tr4w/src/domain/uLogBackup.pas#L457) · [Backup default](../tr4w/src/uSettingsModel.pas#L5916)

## Findings in priority order

### 1. High · A QSO can leave the station before it is saved

`LogContact` queues the live multi-op packet and the UDP, HamScore and applicable external-logger event before `tAddQSOToLog` attempts the append. The read-only precheck helps after a failure has already been detected. If the first write fails, or the process exits between queuing and committing, the server or a downstream logger can have a contact absent from the station database. Retrying Enter allocates a new network sequence, so the server's identity-based deduplication cannot join the two attempts. The receive path also queues its enabled event before the local append and ignores `LogContact`'s Boolean result. `c411a172` recorded the outgoing ordering gap under issue 340. [Live send and append order](../tr4w/src/trdos/logsubs2.pas#L1864) · [Dispatcher sinks](../tr4w/src/trdos/logsubs2.pas#L3315) · [Peer receive path](../tr4w/src/uNet.pas#L1023)

Make the local commit the release point for those events. Capture payload inputs that depend on the pre-QSO score sheets before they change, then release the payload only after success. Preserve the existing resend flags and durable logger queue. The multi-op sent flag currently means a socket write completed. If end-to-end delivery must guarantee a durable server copy, it needs an acknowledgement from the server's committed store. Synchronize can help reconcile missing rows today. [Socket completion](../tr4w/src/uNet.pas#L3207) · [Catch-up behavior](NETWORK_LOG_AUTO_SYNC.md)

### 2. High · One county-line, multi-park or rover entry can save only some legs

`TryLogContact` commits the first row, then `DrainPendingMultiQSORefs` commits each subsequent leg. If a later write fails, the earlier rows already exist while the UI reports the entry as refused and preserves the original text. The next Enter reparses the whole exchange and can append a previously saved leg. A process exit between legs can also leave a structurally sound database with an incomplete contact. The historical plan explicitly retained per-row commits. The full-disk bench checklist now expects the entry to be refused as a whole, and current code cannot meet that expectation when a later leg fails. County-line ADIF export also relies on the saved linked set. [Leg writes](../tr4w/src/MainUnit.pas#L962) · [Refusal and retry](../tr4w/src/MainUnit.pas#L1288) · [Historical decision](SQLITE_LOG_SCHEMA_PLAN.md#L1434) · [Bench expectation](BENCH_QUEUE.md#L333) · [Grouping](../tr4w/src/uLogRepository.pas#L3652)

Treat the complete operator submission as one transaction and publish each leg after that transaction commits. Reuse the repository's transaction handling from ADIF import and multi-op catch-up, while preserving live sent-exchange capture, scoring and delivery metadata. Keep a single commit for the usual one-row submission. Inject a failure on the second leg and at commit, then verify zero rows and zero events on refusal and exactly one complete set after retry. [Batch append](../tr4w/src/uLogStore.pas#L3347) · [Repository transaction](../tr4w/src/uLogRepository.pas#L4036)

### 3. High · Edit QSO and Alt-Y do not wait for a confirmed mutation

The edit form can close as saved because `SaveQSOToEditableLog` starts with `True` and the store's update procedure returns no status. The first failed edit can still send the network or dispatcher event, lose the edited fields when the dialog closes, and leave the original row intact. Alt-Y similarly posts a delete or restore event and toggles its state before the rewrite. It then sends the peer update and shows a success message without a commit result. Both prechecks cover a log already read-only. A write failure discovered by the mutation itself still takes the unconfirmed path. [Edit save](../tr4w/src/uEditQSO.pas#L569) · [Edit and network order](../tr4w/src/uEditQSO.pas#L941) · [Form close](../tr4w/src/ui/lcl/uEditQSOForm.pas#L1373) · [Alt-Y](../tr4w/src/trdos/logsubs2.pas#L648) · [Store updates](../tr4w/src/uLogStore.pas#L3075)

Return a committed outcome from the store and check that the intended row was updated. Keep a refused edit open with its fields and defer delete/restore UI state and outbound messages until commit. Run the same first-write failure checks against insert, edit, delete and restore.

### 4. High for responsiveness · The logging thread pays for backup and lock waits

When a periodic backup is due, the Enter handler waits for `VACUUM INTO`, verification and publication. With an external destination it also pays for a local outbox copy before the remote worker takes over. The main SQLite connection has a 2,000 ms busy timeout. The stale-snapshot retry addresses a different failure mode where waiting on a stale read transaction cannot help. WAL checkpoints can also add work to some commits. The schema plan's historical harness recorded 329 ms for 500 repository `SaveQSO`/`Commit` pairs, about 0.66 ms per pair on that run. That aggregate covers the storage loop. It cannot establish Enter-to-ready latency or the slowest saves during a contest. [Periodic backup](../tr4w/src/trdos/logstuff.pas#L6367) · [Outbox submission](../tr4w/src/uBackupCopyService.pas#L383) · [Busy handling](../tr4w/src/uLogStore.pas#L1020) · [Recorded benchmark](SQLITE_LOG_SCHEMA_PLAN.md#L1472) · [SQLite checkpoint behavior](https://www.sqlite.org/wal.html#performance_considerations)

Measure Enter-to-commit and Enter-to-ready separately at p50, p95, p99 and maximum. Include a large contest log, an open search window, a backup due, and concurrent delivery writes. If backup dominates the tail, move the periodic snapshot, verification and outbox work to one worker with its own connection and a stable log path. Coalesce requests per log, preserve failure reporting and keep pre-clear and pre-upgrade operations gated on successful backups. Keep synchronous local commit as the acknowledgement boundary. [Separate snapshot connection](../tr4w/src/domain/uLogDatabase.pas#L1750)

**Status (issue 350, 2026-11-22): built, not yet measured.** The periodic backup's snapshot, verification, publication and outbox copy now run on one worker thread (`uLogBackupWorker`, glue `uPeriodicBackupService`) whenever the log is in WAL. The worker opens its own read-only connections for each run. Requests coalesce: a request made during a run produces one more run. Results reach the main thread through `Application.QueueAsyncCall` and take the same reporting path as before, including the issue 351 failure reminder and the age-based trigger. A rollback-journal log still backs up inline, because a reader there would block the commit. Pre-clear, pre-catch-up and pre-upgrade backups stay synchronous, and no restore operation exists yet. The measurement instrument is `tr4w/test/bench/bench_enter_latency.lpr`. It times commit-only, inline-backup and worker phases over a large scratch log and reports p50, p95, p99 and max. Its numbers are pending on the station (BENCH_QUEUE.md). The bench does not cover the UI parts of Enter-to-ready (grid, windows, search, delivery).

### 5. Medium · Recovery readiness needs explicit checks

- **Storage mode.** The app requests WAL and reads back the actual journal mode. It sets `synchronous=FULL` without reading that value back. SQLite documents weaker power-loss durability with `FULL` in rollback-journal mode and an extra directory sync with `EXTRA` in `DELETE` mode. Use a local live database for each station, with TR4W multi-op sync or a backup destination for remote copies. Expose the effective mode, synchronous setting and loaded SQLite version in the startup diagnostic. Verify `EXTRA` on any rollback-mode storage configuration the project intends to support for live logging. [TR4W pragmas](../tr4w/src/domain/uLogDatabase.pas#L1404) · [SQLite durability matrix](https://www.sqlite.org/pragma.html#pragma_synchronous) · [SQLite WAL filesystem requirements](https://www.sqlite.org/wal.html#overview)
- **Backup freshness.** The periodic counter starts at zero each session and resets even after a failed snapshot. A short session may therefore produce no new backup, and a failure delays the next attempt by the configured number of logged records. The backup status is posted before the successful Enter path clears the status line. A persistent last-success timestamp and a visible failure state would let the operator see the age of the recoverable copy without adding work to every save. A local backup on the same failed device provides no independent recovery. Test restore from a configured second destination and compare QSO identities and linked sets. [Backup scheduling and status](../tr4w/src/trdos/logstuff.pas#L6367) · [Status clear](../tr4w/src/MainUnit.pas#L1335)
- **Full disk at startup.** The runtime recovery branch needs an open repository. A full-volume error during startup can instead disable the store, as `c411a172` records. Keep the startup refusal explicit and offer a retry or a verified read-only reopen for an existing healthy, current-schema log where SQLite can open it. Preserve the existing refusal when integrity verification fails. [Startup writability gate](../tr4w/src/uLogStore.pas#L2295) · [Runtime recovery gate](../tr4w/src/uLogStore.pas#L1448)

## Verification and release checks

- **Windows unit runner.** Ran the existing `tr4w_unit_tests_fpc.exe` to completion. It reported 350 suites, 533,747 passing checks and zero failures. The executable was already built in this workspace. Relevant current test sources cover write visibility before commit, lock contention, simulated `SQLITE_FULL`, recovery after clearing that condition, WAL-inclusive snapshots and refusal to migrate when the backup fails. The commit `c411a172` separately records NY4I's real full-drive bench. [Repository tests](../tr4w/test/unit/uTestLogRepository.pas#L2033) · [Disk-full test](../tr4w/test/unit/uTestLogStore.pas#L1816) · [WAL snapshot test](../tr4w/test/unit/uTestLogDatabase.pas#L1439) · [Migration refusal test](../tr4w/test/unit/uTestLogMigrationBackup.pas#L218)
- **Bundled SQLite recovery check.** Loaded the Windows x64 SQLite DLL and confirmed version `3.53.4`. The installer, redistributable and test DLLs in the workspace were byte-identical. In a scratch database using `WAL` and `FULL`, a forced process exit after one commit and during a second transaction preserved the first row, discarded the in-flight row and passed `integrity_check` on reopen. A copy of the main `.db` alone opened and contained zero rows. This exercised the SQLite runtime with a process exit. Actual power-loss behavior and the TR4W GUI acknowledgement sequence were outside that check. Also verify the loaded library in Linux and macOS release builds, since they can pick up other versions and SQLite documents a rare multi-connection WAL corruption bug in older releases. [Runtime packaging](UPDATING_RUNTIME_DLLS.md#sqlite3dll--the-one-that-fails-differently) · [Linux packaging](INSTALL_LINUX.md#packages-to-install) · [SQLite WAL-reset fix](https://www.sqlite.org/wal.html)
- **Application release check.** On an isolated contest, record the exact set of acknowledged rows. Terminate the application before and after commit, reopen with the WAL present, and compare row identities, exchange fields, sent serials and linked sets. Repeat with a forced write failure, a held lock and a failure on a later leg. Verify the retained input, outbound events and restored backup against the same expected rows. Run a separate power-loss test on disposable representative storage if the release claims that behavior. Keep the latency measurements with those results.
